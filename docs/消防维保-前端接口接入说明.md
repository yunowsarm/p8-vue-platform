# 消防维保前端接入说明

依据：后端《接口文档-养护管理.md》及2026-10-16确认的业务规则。

## 本次接入

入口仍为 `src/views/smartIOT/security/fireAlarm.vue`，五个工作区保持不变。页面改为加载后端数据，不再使用消防维保仿真数据。

接口声明位于 `src/service/api/modules/maintenance.js`，由平台自动注册：

| 命名空间 | 后端路径 |
|---|---|
| maintenanceDeviceType | /jt/maintenance/deviceType |
| maintenanceDevice | /jt/maintenance/device |
| maintenancePlan | /jt/maintenance/plan |
| maintenanceRecord | /jt/maintenance/record |

每组声明list/add/edit/delete/queryById。沿用平台现有服务地址、登录请求头；路径未额外添加`/czwj`。删除通过POST的Query参数传id，其余写入使用JSON。

四类资源仅在新增（add）时，于JSON正文统一携带`createTime`，值为请求发起时的浏览器本地当前时间，格式`yyyy-MM-dd HH:mm:ss`，精确到秒。列表查询及编辑不自动添加该字段。

`src/service/maintenance.js`统一解析`{ code: 200, success: true, result/data }`、旧平台`head/data`及全局拦截器解包后的分页/详情对象。写入兼容解包后的“添加成功！”、“编辑成功！”、“删除成功！”与null结果；明确失败标记及失败文本仍会拒绝。新增/编辑后重新读取对应资源列表取得后端生成的ID，无关列表失败不影响本次保存确认。错误提示标明设备类型/设备/计划/记录及具体操作。

设备类型管理每次打开都会查询类型列表。新建/编辑设备前刷新类型候选，新建/编辑计划前刷新类型、设备及完成状态；执行登记前重新查询计划、设备与记录，避免按旧状态登记。工作区切换时刷新相关列表。刷新请求共用队列，避免旧请求覆盖新数据；同组查询失败不做部分替换。服务端已保存而页面回调或列表同步失败时提示“操作已成功，无需重复提交”，不会误报成保存失败。

## 已确认的页面规则

- 一个计划只关联一台设备，每台设备只允许新建一个周期计划。设备候选来自台账，已有计划的设备显示“已有计划”并禁选；台账提供“查看计划”代替重复安排。提交前刷新设备、计划及记录，重新检查关联冲突，编辑时排除自身计划。历史重复计划不自动删除，允许原设备上的资料编辑，但禁止增加新的重复关联。
- 主键id与设备编号deviceCode分开；关联计划、记录使用主键，不用展示编号代替。
- 登记结果仅使用“合格”“不合格”，两种结果都算本期已执行，每条有效记录推进一期；不合格须说明问题。
- 计划持续按周期执行，无需每期新建。planDate保存第一次维保时间，frequency必填；当前待维保时间由首次时间加已登记次数对应的周期计算。实际登记日期不改变后续排期。
- 例：首次2026-10-16，每月；10月20日登记后，下次为2026-11-16。月底始终按首次日期定位：1月31日→2月28日→3月31日，闰年同理。逾期登记每次只推进一期，不跳过未执行期次。
- 设备下次维保取关联计划当前待执行日期中的最早值，包含逾期；无计划显示“未安排计划”。缺首次日期或频率的计划须先补齐，不生成虚假到期日期。
- 不合格记录统计为历史记录数量，不推断成设备当前故障状态。
- 登记唯一入口保留在计划列表；台账和提醒引导查看计划，记录列表只读。
- 设备表单只保留设备编号、类型、名称、品牌、型号、安装位置、安装日期；台账列表、搜索和档案详情不再展示设备负责人。编辑时保留后台已有负责人值，避免隐藏字段后误清空历史数据。
- 负责人只在计划中维护，不再从设备负责人自动带入。计划日期统一展示为“第一次维保时间”，仍按后端planDate的yyyy-MM-dd日期格式保存。
- 计划已移除“提前提醒天数”输入，新计划不再发送隐藏的默认7天；编辑历史计划时保留已有后台提醒配置。提醒列表按后台实际返回的配置计算，不修改旧计划。
- 登记保留记录名称、关联计划/设备、计划负责人、实际日期、合格/不合格、备注、附件；关联计划、设备、本次维保时间、下次时间、计划负责人禁用编辑；记录名称默认按计划和期次生成，允许修改且必填，提交时保留填写的名称并继承最新计划负责人。实际日期、结果、备注和附件可填写。
- 移除检查模板、费用、执行单位、更换部件、二维码、仿真打印、仿真留痕及没有后端接口的全局通知规则。
- 台账历史记录可进入详情，详情保留“返回设备档案”。

计划列表展示当前期状态：无记录且未进入登记窗口为“待首次维保”，已有记录且下期未进入窗口为“待下期维保”，提前7天内为“即将到期”，当天“今日到期”、超过日期“已逾期”；缺日期或周期仍提示补齐。台账状态列及筛选名称统一为“维保计划”；日期提示保留关联计划名称，鼠标采用普通指针。

计划及维保记录的列表、表单和详情不再展示养护类型。新计划及新登记不发送maintenanceType；编辑旧计划时仅在详情原本包含该字段时保留原值，避免隐藏后清空历史数据。

## 流程补全

- 没有设备类型时，新建设备弹窗提供“添加设备类型”入口，新增后保留设备表单；类型只有一个时自动选中。
- 没有设备时，计划列表和计划弹窗提供“先添加设备”入口；台账行和无待执行计划的设备详情提供“安排计划”，自动带入该设备。
- 计划列表展示首次时间、下次维保时间、已维保次数，提供“执行登记”“查看记录”。登记弹窗展示本期计划时间和登记后的下次时间。已有记录后不允许修改有效的首次日期、周期或设备，避免历史排期变化；可修改名称和负责人。历史缺失的首次时间或周期允许补齐。
- 登记保存后仅刷新记录，不覆盖首次日期，也不新增计划。基于后端持久化的首次日期、频率及同计划同设备有效记录数重新推导日期，刷新页面后结果一致。
- 新建和编辑计划要求有效计划日期；接口已有无日期记录标为“待定日期”，补齐后再执行登记，避免长期没有提醒。
- 登记日期不能晚于今天；不合格须填写问题及处理说明。提交前重新读取设备、计划和记录，比对打开弹窗时的期次及计划时间，发现该期已被其他人登记则阻止提交。执行登记在本次维保时间前7天开放，到期当天及逾期仍可登记，提前8天及更早不可登记。打开入口及提交均校验最新期次和登记窗口，不受后台提醒天数影响；到期提醒沿用现有配置。
- 登记成功后关闭登记弹窗并刷新周期日期，保留当前工作区及筛选，不再自动跳转到维保记录；需要时从计划行主动查看记录。
- “正在提交/读取”与“读取失败”分开：读取失败时阻止继续提交，但允许关闭弹窗，并保留已填写内容供重试。
- 已关联计划或记录的设备删除按钮置灰并说明原因，不让用户点到确认后才发现无法删除。

当前接口没有计划有效/暂停/终止字段，因此现有计划均视为占用设备；未登记计划可删除后重新安排，有历史记录的计划继续保留。后端应提供设备计划唯一性校验（并发请求须在事务中保证），并在后续增加终止能力后释放设备。

跨终端同时提交的最终唯一性、历史记录更正留痕、不合格后的维修闭环仍需要后端提供事务约束或对应业务接口；前端不会伪造这些能力。

## 附件

复用报修等页面的`attachment.upload`，通过FormData字段`thefile`上传真实文件。平台现有axios拦截器将head/data响应解包为附件数组；适配器兼容完整data数组响应，并提取id/attachmentId、name/fileName、url/fileUrl/filePath及size/fileSize。

提交记录兼容文档中的`uploadFiles: [{ id?, name, url, size }]`，并保留平台上传返回的`fileName/filePath/fileType`字段，避免后端附件关联丢失。filePath按报修组件约定保存存储文件名，url保留访问地址。不发送File对象、Element Upload的uid或临时状态。详情同时兼容id/attachmentId、name/fileName、url/fileUrl/filePath、size/fileSize，统一用于展示与下载。自定义上传先通知Upload进入uploading状态；上传未完成不能移除附件、提交或关闭登记；上传失败可移除失败项后重试。附件非接口必填项，不伪造占位文件。

列表不展示附件数量，因为后端列表不返回附件。打开记录详情时调用queryById读取真实附件；有附件ID时复用`attachment.download`，否则使用有效的附件访问地址。上传使用同一响应解析器，明确失败的head/data不会误收为附件；下载返回JSON/HTML错误正文时显示错误，不下载为假附件。

## 数据读取及边界

为保证跨工作区统计、候选设备、周期排期与历史记录完整，目前按后端分页接口逐页读取四类数据，再在页面筛选分页。不会把第一页作为完整数据，也不会在读取失败时回退仿真数据。后端重复返回同一页、数据不完整或读取失败时显示错误并禁止继续写入，重新加载成功后恢复。

当前后端没有总览/提醒/批次接口，也没有期次、下次维保日期字段；总览与提醒来自完整设备、计划、记录集合。当前日期推导要求planDate始终为首次日期，后端不得在登记后将该字段覆盖为下次日期，否则会重复推进。若后端增加当前期次和下次日期，应切换为后端统一计算，并为记录保存本期应执行时间。大规模台账可由后端补充聚合查询与服务端分页后再优化读取方式。

保存时防止页面重复点击；接口没有幂等键、版本或任务唯一约束，因此前端不能保证多终端并发登记的数据库唯一性，需后端负责最终约束。本次未接入记录编辑/删除入口，保持已有的单一登记流程。
